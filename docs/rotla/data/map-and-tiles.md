# マップ作成・タイルデータ

[設計目次](../README.md) / [保存仕様](../runtime/hotseat-and-save.md)

Luna作成案を統合し、既存初期化順と公式配置条件に合わせて整理した設計。
ここに記す新しいクラス・フィールド・関数は提案API。

## 1. 初期実装と後続実装

初期実装は4人ロングの固定マップ。配置フェイズ試作では、正式な部品図の代わりに
33枚の仮3ヘックスタイルと首都プロジェクト3枚を使う。全体を構成する公式マップ用3ヘックス33枚と
首都プロジェクト3枚の正式な構成は引き続き台帳で確認し、ショートの除去処理は作らない。

線路タイル135枚はマップ用タイルとは別在庫。
[PDF内部配置から作成した線路タイル台帳](track-tile-ledger.md)で54種類・135枚を確定した。
辺接続、hub spot数、収益、特殊記号系列をベクトル化し、Engine DSLへ接続済み。

固定マップにも自由マップと同じ変換器を使い、宣言データ→ヘックス集合を生成する。
ただし初期段階で自由配置ウィザードのUIまで完成させる必要はない。

自由マップは **本ゲーム作成前のウィザード** とする。Hotseat試作はNew Game画面内に配置フェイズを表示し、
33枚の配置完了後に3枚の首都プロジェクトの対象都市を選び終えるまでCreateを無効にする。
Base初期化後にhexesだけ差し替える方式は採らない。
完成した配置をsettings.rotlaに入れ、Game.loadで渡し、game_hexesで展開する。
会社の予約ホームもinit_hexesの予約生成前に同じ配置から計算する。
Adaptiveの実際のホーム選択は設立時なので、ここで勝手に確定しない。

## 2. データモデル

| 要素 | 提案フィールド |
|---|---|
| タイル種別 | type_id, local_hexes, source_ref |
| 物理個体 | copy_id, type_id。複数枚の同型タイルを区別 |
| 各ローカルhex | axial[q,r], terrain, city_type, paths, boundary, home_ref |
| 配置 | copy_id, origin[q,r], rotation(0..5) |
| プロジェクト適用 | project_copy_id, target_city_id, effect_type |
| 完成マップ | map_id, map_version, placements, projects |
| 線路在庫 | tile_id, color, count, code, upgrade_refs |

定義には図柄・相対位置だけを持ち、原点と回転は配置情報に置く。
マップIDや座標は説明例であり、未検証の公式盤面を作成済みとしない。
固定シナリオの配列・Hashをゲーム間で共有して破壊しない。

`city_type`は都市hexを`basic`、`capital`、`company`のいずれかに分類し、都市のないhexでは
`nil`とする。都市番号ではなくhexに属する意味情報なので、タイルがアップグレードされた後も
そのhex上の現在の`Engine::Part::City`全件へ適用する。線路が印刷済みかどうかは都市分類に
影響しない。Adaptiveのホーム候補は`basic`都市だけを起点にし、空き・予約・トークンの動的条件は
設立時に別途検査する。座標名から首都や会社都市を推測しない。首都プロジェクトによる分類変更は
プロジェクト効果の実装時に加える。

## 3. 座標・回転

内部の配置計算はaxial座標、表示先は既存Engine::Hexの座標へ変換する。
回転の向きは1箇所で固定する。例えばcube座標
(x,y,z)=(q,-q-r,r)に対して1ステップを(-z,-x,-y)とする場合、
軸座標は(q,r)→(-r,q+r)になる。
この定義と画面上の時計回り、Engineの辺0〜5の対応表をW03で確定する。

`expand_tile(definition, placement)`（提案）は次を返す。

- 各hexの最終座標と安定した地物ID
- 回転した線路の出口、境界、ホーム・都市の対応
- 既存DSLへ渡すcodeと予約情報

軸の平行移動だけでなく、印刷線路の辺番号も回転させる。
既存Hexの文字/数値座標範囲に収まるよう、完成マップ全体を決定的に正規化し、
変換の逆写像を保持する。回転6回で原形、変換往復で同座標というテストを必須にする。

## 4. 配置確認

`validate_placement(draft, placement)`（提案）は変更を行わず、
合法性と理由コードを返す。確定操作でも再検証する。

| 確認 | 判定 |
|---|---|
| 入力 | 既知の未使用copy_id、整数座標、rotation0..5 |
| 重複 | 3hex内部にも既存盤面にも重複がない |
| 接触 | 最初の遠隔地タイル以外は、既存盤面と異なる境界辺を3本以上共有 |
| 数え方 | 頂点接触は0、同じ辺の二重計上なし、隣接タイル数ではない |
| 黒境界 | 黒い境界ヘックスに他のhexが辺を共有する配置を拒否。線路の有無に関係しない |
| プロジェクト | 通常の3hex配置ではなく、合法な都市を選択して効果を適用 |
| 完成条件 | 全必須物理タイルとプロジェクトを処理、ホーム/都市/地形参照に欠落なし |

最初のタイルは遠隔地タイルを中央へ置く。初手に3辺共有を要求しない。
ルールにない「既存線路とつながらないから配置不可」という制限は追加しない。
配置不能なプロジェクトの山の底への移動、合法配置不能なマップ全体の作り直しは
紙面p.6の手順をW10で実装し、勝手なタイル削除で解消しない。
補助の単hexタイルは任意要素として、採用する固定マップで使うなら明示する。

## 5. 自由マップUIとSetupJournal

画面は盤面、公開中タイル、回転、候補位置、確定ボタン、次の担当者を表示する。
候補は半透明プレビュー。無効時には理由を表示する。
クリックのプレビューはdraftだけを変え、会社金庫・株・本ゲームActionには触れない。

確定した操作をSetupJournal（提案）へ記録する。
種類はreveal/place/choose_project_target/restart等。現在の試作はplaceとchoose_project_targetを保存し、
行為者、copy_id、原点、回転、対象IDを保持する。
これは既存Engine::Actionではなく、ゲーム作成前の専用履歴である。
本ゲーム開始後の行動は引き続きEngine::Actionだけで変更する。

seedは引く順番に使い、人が選んだ配置の代わりにはならない。
再開時は残り山・現在公開中タイル・担当者・履歴からdraftを復元する。
確定時はjournalを再検証し、検証結果の真偽値だけを信用してゲームを開始しない。
本ゲーム開始後に配置を変えたい場合は新規draft/別ゲームを作る。

Hotseatで伏せるのは未公開の山。現在公開中のタイルや完成盤面は全席に見せる。
画面に山の将来順を表示しないが、単一PCの内部JSONを秘密保護する仕組みは初期要件ではない。

## 6. 検証と素材

- 6方向で位置・線路端・境界が整合する。
- 2辺接触拒否、3辺接触許可、複数タイルにまたがる3辺を許可。
- 同型タイルの別copyは使用可、同copyの再使用は不可。
- 首都対象選択、対象なし、再開時の同じ公開タイルを検証。
- 同じ確定manifestから同じcity ID・予約・グラフを生成する。
- 既存 /map と /tiles の開発ルートで表示を確認する。

原画の再配布条件が未確認なら、線路・都市・地形を独自の簡素な描画で表示する。
台帳に参照資料と確認状態を持ち、見えないタイル枚数を仮定で公式値扱いしない。

実装チケット：固定W01/W03、自由W10。検証：検証計画の「マップ」。
