## 3. 作業を小さく切る境界

W05は「先行購入と通常購入」「資本発行」「敷設と経路」「配当」に分けられるが、
ステップ順と資金の受渡しは先に統合仕様を固定する。
W06の能力は個別に実装できるが、合併後の所有・使用済み状態は共通契約へ統一する。
各担当が別々の正本を持つ現金・能力・設定モデルを作らない。

## 4. まとめ役と実働役

Sol：着手範囲と受入条件の整理、原典/既存エンジンとの差の確認、変更後レビュー。
Luna：限定したチケットの文書・実装・対象テストを作成し、残る不確実性を報告。
統合担当：共有ファイル競合を調整し、差分と検証結果を確認してブランチへ反映。

モデル名で正しさを保証せず、入力、変更範囲、期待値、根拠を各作業へ渡す。
仕様未確定のW01や共通エンジン変更はレビューを厚くし、
部品データ整備・限定Step・既知ケースのテストを実働役へ渡す。
同じファイルの同時編集は避ける。小さな作業では引継ぎコストも判断する。

## 5. 各変更の提出条件

- 何が合法/非法になるかと、根拠資料または設計決定を示す。
- 変更ファイルと関連する状態/Actionを示す。
- 実行したテストと結果、未実行部分を区別する。
- 保存への影響と既存タイトルへの影響を確認する。
- 未解決事項を台帳へ戻し、必要なテストをpendingのまま完成扱いにしない。
