# 検証計画

[詳細設計の入口](../README.md)

## 1. 判定原則

初期完成は4人ロング、検証済み固定盤面、12小会社の能力、合併、6サイクル、Hotseat保存復元。
ショート削減を省けても、能力・終局処理は省略しない。
各テストは前提、Action、期待状態を持つ。実装した関数の出力をそのまま期待値にしない。

## 3. 全12能力

[能力表](../rules/mergers-and-abilities.md)の12社それぞれについて、
正常使用、非法使用拒否、合併後、保存復元の4観点を用意する。
複合能力は少なくともOvernightの接続判定、Resourcefulの廃車保持、
Expressの対象列車、Expansiveの未使用枠を扱う。
原典で未解決の組合せはpendingとし、黙って通常ルールを当てはめない。

## 4. マップ

回転0〜5、重複、接触2辺/3辺、異なる既存部品にまたがる3辺、
黒境界隣接、首都配置、配置不能時の処理、同seed・同選択の再現を検証する。
座標変換は六回回転で原状復帰し、辺の接続が両方向で一致することを確認する。
最初の完成条件では固定マップの都市値、予約、辺、地形費用、線路枚数を照合する。
自由マップUIの受入は後続工程。

## 5. 実装上のテスト配置

提案配置はspec/lib/engine/game/g_rotla/。既存規約に合わせて最終決定する。
短い状態遷移はunit spec、長い操作列はfixtureで検証する。
[fixture規約](../../../public/fixtures/README.md)に従い、完走fixtureはfinished、
loaded、resultの期待値を持たせる。
Toolsで強制終了した短いfixtureは、公式6サイクル完走の代わりにならない。

実装後の候補コマンド（今回未実行）：
```sh
docker compose exec rack bundle exec rspec spec/lib/engine/game/g_rotla
docker compose exec rack rake
```

対象specから始め、共通Action・Base・UIを変えた場合は関連タイトルと全体ゲートを実行する。
rakeは既存のコンパイル・spec・Rubocopを含むため、結果と対象コミットを記録する。
文書追加そのものはリンク・構成・整合性を検証し、ゲームテスト成功とは報告しない。
