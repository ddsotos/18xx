## 1. 目標と最初の完成形

既存の18xxエンジンに Railways of the Lost Atlas（以下RotLA）を追加し、
自分のPC上のブラウザで、1人が全席を操作して研究する、または4人が交代して遊べるようにする。
ローカルは「localhostで動く既存Webアプリ＋Hotseat」と定義する。
AI対戦や公式ソロモードを意味しない。

最初の完成形は、**4人・ショートゲーム・検証済み固定マップ・拡張なし**。
8小会社の対象能力、合併、4サイクル終了、得点計算まで実装し、1ゲームを完走できることを基準とする。
2〜3人ショート、3〜5人ロング、自由なマップ作成、マイクロゲームは後続段階とする。
固定マップは任意の縮小盤面ではなく、公式の構成制約を満たすものを選ぶ。

今回の成果物はこの方針文書のみ。RotLAが現在のゲーム一覧から遊べる状態になったわけではない。

3. 固定マップの全ヘックス・向き・都市値・会社ホーム・首都・遠隔地。
4. 遠隔地収益カードの選択とフェーズ別収益。
5. 合併時の株式交換・社長決定・トークン・列車上限処理。
6. Resourcefulの廃車後1回運行など、通常の廃車と異なるタイミング。

紙面p.2（PDFの3ページ目）のCOMPONENTS図にはタイル構成があるが、
重なった線路タイルの個別枚数は図だけで断定しない。

## 5. 必須ルールと実装上の注意

### セットアップ・株式

- 4人の初期所持金は275。ショート8小会社、ロング12小会社。
- 競売は最低120、5刻み。特定会社の固定競売ではなく、落札者がその時点で設立可能な会社を選ぶ。
- 小会社の設立資金は落札額の全額。初期株価は落札額の半分を、そのフェーズで許される株価へ切り下げる。
- 黄色の初期株価は60/70/80/90。後のフェーズでは範囲が拡張される。
- 設立で社長証券40%を得る。会社から買う株の代金は会社へ、銀行プールから買う代金は銀行へ。
- プレイヤーの保有上限60%、銀行プール上限50%、初回運営前の小会社株は売却不可。
- 通常の売却による下落は同じ手番で同社を何株売っても1段階。初期版の解釈や「1株ごと下落」バリアントと混同しない。
- 売り切れ上昇・社長交代・売却後の同一SR内買戻し禁止も実装する。

### 運営と列車

順序を専用Stepで明示する：

1. 新設小会社の初回だけ、任意で先行列車購入。
2. 任意で自己株式1株の発行または買戻し。
3. 線路敷設・アップグレード。
4. トークン配置。
5. 運行。
6. 全額配当または全額留保。
7. 通常の列車購入、必要なら強制購入。
8. 次の会社へ。

初回の先行購入は列車山・銀行プールから定価、かつ会社資金のみ。
他社からの購入は通常の列車購入で行う。社長双方の合意が必要で最低価格1。
先行購入の時点で、後続Stepの株式発行や個人資金を先取りしない。

強制購入は会社現金を先に使い、その後に個人現金、必要な株売却へ進む。
未発行株を強制購入処理で自動発行しない。
直前に別会社から受け取った配当は、そのプレイヤーの現金として使用できる。

| 項目 | 基準 |
|---|---|
| 小会社の列車上限 | 黄色・緑2台、紫・灰色1台 |
| Spacious | 通常上限+1（ロング等で導入時に対応） |
| 列車価格 | 2=100、3=200、4=300、5=450、6=550、7=750、∞=1000または規定の下取り |
| 通常の廃車 | 4で2、6で3、7/∞で4 |
| フェーズ移行 | 対象列車の購入・輸出に従い即時反映。上限超過の整理を行う |
| ローカル運行 | ホーム都市だけの1停車運行を許す。通常の「必ず2停車」を流用しない |

経営順は株価降順・同値は株価列への到着順。運営中の株価下落で同じ会社が二度運営しない。
小会社の1株配当は総配当の20%。会社が自己保有する株にも配当する。
株価上昇は総配当額と現在株価の比較で0/1/2段階を決定する。
全額留保・収益0では1段階下落し、株価0での会社解散も処理する。

### 合併・輸出・終了

SR → OR1 → OR2 → 合併（条件を満たす場合）→ 輸出 → 次サイクルを基本構成とする。
ショート4サイクル、ロング6サイクル。
最終サイクルの合併・輸出・終了判定の順は紙面pp.18〜19と照合してテストで固定する。

合併は他社との接続、双方社長の同意、株式交換、社長決定、
会社資金・列車・トークン・固有能力の引継ぎ、平均株価の切下げを一連の処理として扱う。
1867の合併式をそのまま使わない。
輸出で2列車が選ばれた場合の残り2列車一括除去も実装する。
破産による終了を初期仕様とし、破産者を除いて続行する任意処理は後続にする。

## 6. マップとタイル

最初は検証済みの固定マップをヘックス集合へ展開し、既存のタイルDSLと描画を使用する。
原画の再現より、接続・都市値・トークン枠・境界・地形コストの正確さを優先する。
紫タイルなど既存エンジンとの差分は先に描画スパイクで確認する。

自由マップは後続段階で、3ヘックスタイルを
「部品ID・原点・60度単位の回転」として記録し、そこからヘックスと辺を生成する。
重複禁止、既存マップとの3辺以上の共有、黒い境界の隣接禁止、
プロジェクト処理とホームの対応を検証する。
抽選順だけをseedで決めても配置選択は復元できないため、配置・向きもAction履歴へ保存する。
最初からランダム生成を固定マップに見せかけて実装しない。

タイル台帳にはID、色、枚数、都市値、枠数、辺接続、地形費用、ラベル、
合法アップグレード、資料ページ、確認状態を持たせる。
`TILES.md` の `/map/<game_title>` と `/tiles/<game_titles>/all` で目視検証する。

## 7. PCローカル起動・保存

既存環境を使う予定の手順：

```sh
git clone https://github.com/ddsotos/18xx.git
cd 18xx
git switch docs/rotla-local-play-plan
make dev_up_b
```

ブラウザで http://localhost:9292 を開く。
このブランチは方針文書のみなので、上記だけではRotLAはまだ選択できない。
実装後は Create New Game → Hotseat → RotLA → 4人 → Short / 固定マップで開始する。

Linux、macOSはDocker・Compose・makeを前提とする。
WindowsではWSL2内での実行を第一候補とし、既存DEVELOPMENT.mdのWindows案内に沿って実機確認する。
Apple Siliconは同文書の `DEV_DOCKERFILE=Dockerfile.amd64` 等の案内を検証する。
OS固有のコマンドを未検証のまま全PC共通手順として掲載しない。

HotseatはlocalStorageとJSONのエクスポート/インポートを活用する。
保存互換性にはゲーム識別子、ルール版、モード、seed/初期配置、Action履歴を含める方針とし、
未知の版の読み込み時には明確にエラーを出す。
ブラウザデータ消去で保存が消えるため、JSONファイルとして退避できる導線を確認する。
undo/redo後の分岐も履歴として再現できることを受入条件とする。

初回のDockerイメージ・依存取得にはネットが必要。
セットアップ後、外部ネットワークを切った状態でlocalhostから起動・復元・プレイできるかは別の受入検証とする。
既存DockerスタックはDB等も起動するため「Hotseatなら既存サーバー依存が一切不要」とは断言しない。
単独静的配布やElectron等のデスクトップ化は、Hotseat完成後に必要性を評価する。

## 8. 実装段階と完了条件

| 段階 | 作業 | 完了条件 |
|---|---|---|
| 0：基盤と仕様台帳 | 既存ゲームをローカル起動、採用版・タイル・列車枚数を確定、RotLA Metaと固定マップ描画を試す | 既存Hotseatが動作し、RotLAのデータ不足が一覧化される |
| 1：最初の1サイクル | 4人セットアップ、設立競売、売買、運営順、初回購入、発行、運行、配当、通常/強制購入 | 下記の序盤シナリオをUIとRubyテストで再現できる |
| 2：ゲーム完走 | 8社の能力、合併、廃車、輸出、4サイクル終了、得点計算 | 4人ショートを完走したfixtureを保存・再生できる |
| 3：ローカル実用化 | 保存/復元、undo/redo、JSON持出し、再起動・オフライン検証、操作案内 | 同じ保存から同じ最終状態・得点になる |
| 4：拡張 | 対応人数拡大、ロングと追加4社、自由マップ、マイクロ | モード別の初期金・構成・終了条件のテストが揃う |

Landmarks、AI、オンライン対戦運営、上流への公開申請は初期完成条件に含めない。
ゲームの成立に必要な合併や固有能力を省いたものは完成版と呼ばない。

## 9. 回帰・受入シナリオ

会話で訂正が多かった箇所を、推奨戦略ではなく資金・手順のテストにする。

| シナリオ | 期待結果 |
|---|---|
| 140で設立＋70で買増し | 個人65、会社210、保有60% |
| 180で設立＋90で買増し | 個人5、会社270、保有60% |
| 140と120で2社設立 | 個人15、各社140/120、各40% |
| 先行会社が40配当、後手会社が1株60で発行 | 個人31、後手会社180。建設費なし・最安列車3=200なら強制購入で個人20拠出、残金11 |
| 上と同じだが先行配当なし、売却可能株もなし | 個人15＋会社180では不足。合法な他社取引等がなければ破産へ |
| 後手会社の先行購入 | 将来の発行や個人現金を含めて200を払う操作を拒否 |
| 他社からの列車購入 | 先行購入では不可、通常購入では双方同意・価格1以上で可 |
| 通常小会社が2列車2台保有 | 3列車の追加購入不可。2列車1台＋3列車1台は可 |
| 初回2購入→1株70発行→追加2購入 | 建設費・収益を除けば140−100＋70−100=10。列車在庫と手順も検証 |
| 40配当時に社長40%、残り60%を会社保有 | 個人16・会社24。総額40を正しく配分 |
| 70開始で80を2回配当 | 他の株価変動なしなら70→80→90 |
| 株価同値・下落・売り切れ上昇 | 順序と「各ORで1回だけ運営」が保存/復元後も一致 |
| 合併・特殊能力・上限整理 | 現金/株式/列車/トークンが重複も消失もせず、能力が引き継がれる |
| 輸出・最終サイクル | 列車購入と輸出のフェーズ処理、終局時点、得点が公式手順に一致 |
| セーブ→ブラウザ再起動→ロード | 現金・株・列車・マップ・次の行動が一致 |
| 同じ序盤から70×3と90×3を別保存で比較 | 分岐を再現できる。最適戦略の保証やAI推薦はしない |

テストはRubyの単体テストとAction fixtureの再生を中心にする。
加えてOpal側でのブラウザ動作、タイルの視覚表示を確認し、Rubyだけ成功して完成とはしない。

実装後の検証コマンド候補（今回未実行）：

```sh
docker compose exec rack bundle exec rspec spec/lib/engine/game/g_rotla
docker compose exec rack rake
```

後者は既存Rakefileのコンパイル・並列spec・Rubocopを含む。
fixtureの配置と実行方法は `DEVELOPMENT.md` および `public/fixtures/README.md` に合わせる。
